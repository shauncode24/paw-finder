# PawFinder

Native iOS (SwiftUI) pet adoption app, built as a student project. **Two roles on one account: adopters browse/apply, listers post pets.** Feature list and phase plan: @docs/SPEC.md. **How listings, lister accounts, and real chat work: @docs/Listers-and-Messaging.md** (read this first for data/backend questions). Colors: @docs/DESIGN.md. Setup: @docs/SETUP.md. Left out: @docs/Leftover.md. Extra polish: @docs/Additions.md.

**Keep it simple.** This is not production-grade. Prefer the simplest thing that works. SPEC.md, ARCHITECTURE.md, and CONVENTIONS.md describe a bigger, modular setup; use them for *what* to build, not for how much infrastructure to add.

## Current phase
Phases 0–5, 7, 9–11, 13 done; 14 partly (App Intents, Handoff; no extensions); 6, 8, 12 skipped for now. **Then: the Petfinder API was removed and replaced by user-posted listings + real chat (docs/Listers-and-Messaging.md).** (update this line as phases complete)

## Setup
- One Xcode project, one app target. The only package is `firebase-ios-sdk` (products: **FirebaseAuth**, **FirebaseFirestore**). Group code by folder: `App/`, `Screens/`, `DesignSystem/`, `Models/`, `Services/`.
- The Xcode project uses folder-synchronized groups, so new files in `PawFinder/` are picked up automatically.
- iOS 17+, SwiftUI, `@Observable` view models, async/await. Swift 5 language mode.
- Navigation: `Router` (selected tab + a `[Route]` path per tab). Add `Route` cases for new screens.
- **No API keys.** The only config file is `GoogleService-Info.plist` (gitignored). `AuthManager.configureFirebase()` must run before anything touches Firestore (see `PawFinderApp.init`); without the plist the app shows "Not connected yet".
- Data: screens use the `PetRepository` protocol (`@Environment(\.petRepository)`). The implementation is `FirestoreListingsRepository`, backed by `ListingsService`: one live Firestore listener on active `listings`; **search/filter/sort/distance run on the phone** (`PetFilters.matches` in `Models/Listing.swift`), so Firestore needs no composite indexes. `MockPetRepository` is **preview-only** (never used at runtime). Listing ↔ document mapping is `ListingMapper`; the lister's form model is `ListingDraft`.
- Screen pattern: an `@Observable` view model with a `State` enum (loading / loaded / empty / error). See `Screens/Discover/DiscoverView` + `DiscoverViewModel`.
- Discover: search and filters live in one `PetFilters` value (saved to UserDefaults, minus search text). The view reloads via `.task(id: filters)` with a short debounce, and refreshes in place when `ListingsService.revision` changes (`DiscoverViewModel.feedChanged`). `PetCard`, `PetPhoto`, and `PetRail` are reusable.
- `Route.petDetail(Pet)` carries the whole pet. `RecentlyViewedStore` (environment) records opened pets.
- Pet detail (`Screens/PetDetail/`): `PetDetailView` + `PetDetailViewModel` (loads the lister via `fetchShelter`, which is a `ListerProfile`; finds similar pets). Owners see edit controls instead of Apply/Message. `PhotoCarousel` has the zoom viewer; `ShelterCard` shows who's listing (map only if the lister gave a street address). `FlowLayout` (DesignSystem) wraps chips.
- Favorites (`Screens/Favorites/`): `FavoritesStore` (environment, `@MainActor @Observable`) saves `FavoritePet` snapshots + `PetCollection`s to `Documents/favorites.json`. `FavoriteButton` is the animated heart (on `PetCard` and the detail toolbar). `refreshStatuses(using:)` re-fetches favorites to detect adopted/removed pets. Mock pet `mock-5` "gets adopted" on refresh to demo this.
- No Core Data or unit tests yet; add them only if a phase really needs them.
- Photos are stored **inside Firestore** (no Storage, no paid plan). Views just use `URL`s: listing photos use a private `pfphoto:` scheme (`PhotoURL`) resolved by `PhotoLoader`; show them with `PetPhoto`/`RemoteImage` (never `AsyncImage`). Shrink uploads with `ImageCompressor` (thumbnail ≈ 280px, full ≈ 900px, chat 800px).
- Extra Info.plist keys (URL scheme `pawfinder`, background fetch, BG task ID) live in the root `Info.plist`, merged with the generated one. Simple keys like permission texts go in build settings (`INFOPLIST_KEY_...`) in the project.
- Logging: use `Log.app/network/storage/location/notifications` (os.Logger), not `print`.
- Deep links: `Router.handle(url)` (`pawfinder://pet/<id>`, `pawfinder://<tab>`, `pawfinder://settings`). `Route.petID` → `PetLoaderView` (uses the saved favorite first).
- Services in the environment: `Router`, `RecentlyViewedStore`, `FavoritesStore`, `LocationService`, `AuthManager`, `ProfileStore`, `ListingsService`, `ListerProfileStore`, `MessagesStore`, `ApplicationsStore`, `NetworkMonitor`, `SavedSearchesStore`, `FollowedSheltersStore`, `CareChecklistStore`, `\.petRepository`. Singletons: `NotificationManager.shared`, `PhotoLoader.shared`, `ShelterGeocoder.shared`, `ListerDirectory.shared`.
- Listers (`Screens/Map/`, `Screens/Shelters/`): the type is still called `Shelter`, but it is a **lister's public profile** (`ListerProfile.shelter()`; id = user ID). `ShelterMapView` pins listers with live listings (coordinates are stored on their profile). `ShelterProfileView` (`Route.shelter(id:)`). `FollowedSheltersStore` follows listers. UI text says "lister".
- Accounts (`Screens/Account/`, `Screens/Onboarding/`): `AuthManager` (environment) wraps Firebase Auth: email **or username** + password (usernames map to `<name>@users.pawfinder.app`) and Sign in with Apple (capability off until there's a paid account). `ProfileStore` (environment) keeps one `AdopterProfile` (name, lifestyle answers) + avatar per user on the device, and moves the guest profile to the account on first sign-in. `OnboardingView` shows once (`@AppStorage("hasCompletedOnboarding")`). `AccountView` has sign out, export (`DataExporter`), and delete (re-auth first).
- Applications: the adopter's drafts live on the phone (`Documents/applications.json`; attached photos never leave the phone). `submit` writes `applications/{id}` to Firestore; the **lister** reviews in `Screens/Lister/ReceivedApplicationsView` and calls `ApplicationsStore.updateStatus`; the adopter's copy follows live (`merge(remote:)`). Form and events are stored as JSON text (`ApplicationJSON`). Routes: `.applications`, `.applicationForm(id)`, `.applicationDetail(id)`, `.receivedApplications`, `.receivedApplication(id)`.
- Messages: **real user-to-user chat**, no simulation. `MessagesStore` listens to `conversations` (participants array-contains me); `ChatViewModel` listens to one chat's `messages` (live socket-style, no polling). Conversation ID = `<listingID>_<adopterID>`. Sends are batched and **not awaited** (Firestore queues them offline = the outbox). "Read" = other's `lastRead` ≥ message time; "typing" = `typing.<uid>` timestamp < 8s old. Start a chat with `MessagesStore.openChat(about:…)` (requires sign-in: set `router.showSignIn = true` for guests). Routes `.messages`, `.conversation(id: String)`; deep link `pawfinder://conversation/<id>`. `ContentModerator` checks outgoing text.
- Notifications: everything is **local** (no push server). `NotificationManager.shared` schedules through `deliver(...)`, which checks `NotificationPreferences` (per-category switches + quiet hours). Call `askPermission(for:)`, never the system prompt directly. New chat messages notify when the app is open (listener) or on the background check (`MessagesStore.backgroundCheck`). Badge = unread chats + new applications received + changed favorites + new saved-search matches.
- Saved searches: `SavedSearchesStore` (environment) + `SavedSearchesView`; the Discover bookmark menu saves/opens them. Run one by setting `router.pendingSavedSearchID` (Discover applies it); deep link `pawfinder://search/<uuid>`. The background task checks favorites, followed shelters, and saved searches.
- **Lister tools** (`Screens/Lister/`): `ListerSetupView` (first-time profile, sets `isLister`), `ListingFormView` (create/edit; photos, all pet details), `MyListingsView`, `ReceivedApplicationsView`. Entry point is the "Rehoming a pet?" section in `ProfileView`. Routes `.listerSetup`, `.myListings`, `.newListing`, `.editListing(id)`.
- Phase 13: `Screens/Swipe/` (SwipeView/SwipeViewModel, `Route.swipe(filters)`), `Screens/Favorites/CompareView.swift` (`Route.compare(pets)`), `Screens/CareHub/` + `Models/CareContent.swift` (built-in content; `CareChecklistStore` in the environment). `router.showInDiscover(filters)` runs a search in Discover.
- Phase 14: `App/AppIntents.swift` (Siri/Shortcuts; intents open deep links via `AppLinks.handler`), Handoff activity `com.pawfinder.viewPet` (declared in Info.plist). No extension targets yet (widgets, Live Activities, share, notification service).
- Additions (see docs/Additions.md): Breeds tab (`Screens/Breeds/`, `BreedMatcher`; tab case is still `.identify`), `DiscoverHeader` (greeting, quick actions, Pet of the day), Profile stats + "Your family", `AdoptionCelebrationView`, Help/About/Privacy/Terms (`Screens/Settings/InfoPages.swift`, `SupportInfo.email` is a placeholder), Settings "Erase all data" (`removeAll()` on each store) and "Show the welcome tour again".
- Backend rules: Firestore **security rules are in `firestore.rules`** (publish in the console; update them when you add collections/fields that need access). **No server to run, no paid plan, no composite indexes, no tests.** Remote push and Cloud Functions are out of scope (docs/Listers-and-Messaging.md §13). Cloud items still not built go in docs/Leftover.md marked *(cloud)*.

## Rules
- Build only the current phase.
- Whenever a phase leaves out or simplifies something from SPEC.md, add it to docs/Leftover.md under that phase (what we did instead, how to add it later).
- Use the `Color.pf*` colors, `Spacing`, `Radius`, and `PF*` components from `DesignSystem/`; no raw colors.
- Screens should handle loading, empty, and error states (`LoadingView`, `EmptyStateView`, `ErrorView`).
- Avoid force-unwraps.
- Never commit keys.
- Ask before adding dependencies.
- Don't run git commands; the user handles git.
